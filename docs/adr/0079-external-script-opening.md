# 0079. 스크립트는 자동 탐색한 VS Code의 기존 창에서 연다

- 상태: 채택·구현
- 날짜: 2026-10-16
- 관련: [0027](0027-windows-editor-packaging.md), [0075](0075-inspector-scope-tabs-and-nested-script-groups.md)

## 배경과 제약

사용자는 스크립트를 더블클릭해 이미 열린 VS Code에서 코드를 보고자 한다. 별도 IDE 설정을 기본 사용의 전제로 두지 않는다. 에셋 ID·공개 스크립트 이름·플러그인 마운트 경로는 기존 참조 계약으로 해석하고, 제공 플러그인 캐시 원본은 수정 대상으로 열지 않는다.

## 대안과 판단 기준

OS 파일 연결은 원하는 편집기를 보장하지 않는다. VS Code 확장은 특정 창 연결을 정밀하게 제어할 수 있지만 설치·연동 비용이 크다. 기본 설치 경로와 PATH에서 VS Code 실행 파일을 탐색하면 별도 확장 없이 마지막 활성 창을 재사용할 수 있다. 여러 창 중 프로젝트별 창의 정확한 선택은 이번 범위에서 보장하지 않는다.

## 결정과 근거

CodeEditor는 소스를 해석하고 실행 계획을 만들며 Windows CreateProcessW로 직접 실행한다. 셸 문자열 실행을 사용하지 않고 argv 인코딩으로 공백·한글·따옴표·역슬래시를 보존한다. 기본 인자는 --reuse-window와 파일 경로다. 설치를 찾지 못한 경우 에디터 공통 settings.json의 codeEditor.executable·arguments로 지정한다. arguments는 문자열 배열이며 {file}을 치환하고, 없으면 파일을 마지막에 추가한다.

에셋 브라우저 Lua 더블클릭과 부착 스크립트 헤더 우클릭의 Open Code가 같은 경로를 사용한다. 기존 Copy ID·접기·원본 찾기 동작을 유지한다. 제공 플러그인은 .labo/CodePreview/<내용 해시>/<파일명>에 읽기 전용 사본을 생성해 열고 원본 캐시는 전달하지 않는다. 이는 실수 방지이며 외부 도구의 의도적인 속성 해제까지 차단하는 보안 경계는 아니다.

script.open CLI는 같은 기능을 제공하고 --dry-run은 실행 계획만 반환한다. 파일 열기를 대상으로 하며 특정 함수·줄로 이동하는 기능은 추가하지 않는다.

## 예상 결과

- 긍정: 일반 설치에서 설정 없이 기존 VS Code 창으로 이동하고 GUI·CLI가 경로 해석을 공유한다.
- 부정: 자동 탐색 실패 시 실행 파일 설정이 필요하고, 여러 VS Code 창에서는 마지막 활성 창이 선택된다.
- 중립: 외부 편집기에서 저장한 코드는 기존 프로젝트 재로딩·Play 경로로 읽는다. 편집기 프로세스 시작 성공은 파일 열기 완료를 보장하는 응답은 아니다.
