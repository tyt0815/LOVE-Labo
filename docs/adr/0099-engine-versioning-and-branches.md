# 0099. 엔진 버전 원본과 배포 계열 브랜치

- 상태: 채택
- 날짜: 2026-10-18
- 관련: [0027 Windows 에디터 패키징](0027-windows-editor-packaging.md), [0088 프로젝트 빌드](0088-project-lua-build-and-game-cli.md)

## 배경과 제약

공개 Lua API·CLI·외부 프로젝트·독립 게임 Export가 있어 실행 파일의 기준 버전을 확인해야 한다. 기존 Git 이력만으로 배포본을 식별하기 어렵고, ProjectInstructions는 development만 표시한다. 기존 파일 형식 버전과 LÖVE 11.5 계약은 유지한다. 아직 정식 배포 태그가 없으므로 시작점은 0.1.0-dev이다.

## 대안과 판단 기준

- UI·CLI·스크립트에 문자열을 각각 두면 불일치가 생긴다. Lua 원본 한 곳을 공통으로 사용한다.
- 실행할 때 Git을 호출하면 배포 사용자의 Git 설치와 저장소가 필요하다. 패키징 시 빌드 정보만 생성한다.
- 버전마다 장기 브랜치를 두면 통합 비용이 커진다. main에서 최신 개발을 통합하고 실제 이전 버전 유지보수에만 release 브랜치를 둔다.
- 엔진 버전과 파일 형식 번호를 합치면 저장 구조가 그대로인 버그 수정에도 데이터 변경이 필요해진다. 독립 계약을 유지한다.

## 결정 및 근거

1. Version은 major·minor·patch·prerelease와 getInfo()를 제공한다. BuildInfo는 소스 실행에서는 빈 테이블이며 패키징에서만 커밋 해시와 dirty 여부를 가진 모듈로 대체한다. 버전 원본 파일은 패키징으로 수정하지 않는다.
2. getInfo()의 engineVersion은 0.1.0-dev, displayVersion은 빌드 정보가 있으면 0.1.0-dev+<해시>[.dirty]이다. revision·dirty는 Git 정보를 알 때만 반환한다. CLI version은 프로젝트 없이 실행하며 기존 응답 version:1은 그대로 사용한다.
3. 시작 콘솔 출력·운영체제 창 제목·새 프로젝트 로컬 안내가 같은 정보를 읽는다. 게임 Export에도 Version·BuildInfo를 그대로 포함하여 제작에 사용한 엔진을 조회할 수 있다. 게임의 버전이나 프로젝트 저장 형식은 변경하지 않는다. 기존 프로젝트 안내를 열 때 자동으로 덮어쓰지 않는다.
4. 0.x에서는 기능·호환성 변경은 minor, 호환성 유지 수정은 patch로 구분한다. 1.0 이후 호환성 변경은 major이다. 배포 준비 동안 dev를 유지하고 작업마다 중복 증가시키지 않는다. 정식 배포에는 변경 내역과 검증을 확인한다.
5. 목적별 작업 브랜치를 사용하며 필요한 이전 배포 계열만 release/<major.minor>로 유지한다. 자동 브랜치 생성은 기존 사용자 변경을 보존할 수 있을 때 수행한다. 커밋·태그·병합·push 권한은 AGENTS.md의 명시적 요청 규칙을 따른다.

```text
창 제목·시작 출력·CLI·프로젝트 안내 ──의존──> Version ──의존──> BuildInfo
packageEditor.ps1 ──생성──> 패키지 내부 BuildInfo (Git 해시·dirty)
GamePackage ──포함──> Version + BuildInfo
```

상속·인터페이스 구현 관계는 없다. Version은 Editor나 Git에 의존하지 않는다.

## 예상 결과

- 긍정: 소스와 배포본의 버전 표시가 일치하고 배포본의 커밋·미커밋 변경 여부를 조사할 수 있다. 브랜치 운영 비용을 제한한다.
- 부정: 버전·변경 내역과 배포 태그의 일치는 배포 시 검증해야 한다. dirty 해시만으로 미커밋 변경 내용을 복원할 수 없다.
- 중립: 자동 업데이트·프로젝트 엔진 버전 제한·데이터 마이그레이션·릴리스 자동화는 추가하지 않는다. Git 없는 소스 실행·패키징은 빌드 해시 없이 동작한다.
